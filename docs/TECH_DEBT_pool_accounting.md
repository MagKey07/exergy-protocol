# Учёт пула энергии (`totalVerifiedEnergyInStorage`)

**Найдено:** 30.07.2026, при разборе с Магом.
**Исправлено и задеплоено:** 30.07.2026, Arbitrum Sepolia.
**Статус:** ✅ **ЗАКРЫТО.**

---

## Что было не так

`totalVerifiedEnergyInStorage` был накопительным счётчиком, а не отражением текущего состояния:

```solidity
totalVerifiedEnergyInStorage += kwhAmount;    // при чеканке
totalVerifiedEnergyInStorage -= kwhConsumed;  // recordEnergyConsumption
```

Вычитание было закрыто на один путь:

```solidity
if (msg.sender != address(settlement)) revert NotSettlement();
```

Энергия уходит из батарей четырьмя путями, вычиталась по одному:

| Путь ухода энергии | Вычиталось? |
|---|---|
| Отдана за ноту через Settlement | ✅ |
| Участник потратил на себя (утюг, производство, 3D-принтер) | ❌ |
| Саморазряд | ❌ |
| Деградация ёмкости | ❌ |
| Устройство отключилось / продано / умерло | ❌ |

Чеканка при этом шла на **каждую** подтверждённую зарядку — потребление в валидации не проверяется вообще (только монотонность циклов, лимит 2 цикла/эпоха и `kwhAmount ≤ ёмкость × циклы`).

**Наверх связь была, вниз — нет.** Пул систематически завышался при нормальной работе участника.

⚠️ **Почему это било именно по нам:** всё предложение Exergy стоит на «обеспечение измеряется, а не заявляется». Дрейф вверх превращал измерение в заявление.

---

## Решение — данные уже были в системе

В `MeasurementPacket` устройство присылает `chargeLevelPercent` — насколько оно заполнено **прямо сейчас**. Поле подписано устройством и со-подписано облаком VPP, то есть проходит ту же двойную проверку, что и всё остальное.

**Оно не использовалось нигде** — единственным упоминанием во всём репозитории было объявление в структуре. Данные собирались, подписывались, доезжали до цепи и выбрасывались.

### Что изменено (3 файла)

**`interfaces/IMintingEngine.sol`**
- в `DeviceCycleState` добавлено `uint256 lastReportedEnergy` (в конец структуры — безопасно для mapping-хранилища);
- в `commitVerifiedEnergy` добавлен параметр `uint8 chargeLevelPercent`;
- новая ошибка `InvalidChargeLevel`, новое событие `EnergyConsumptionReported`.

**`MintingEngine.sol`**
- `totalVerifiedEnergyInStorage += kwhAmount` заменено на `_syncDeviceStoredEnergy(...)`;
- новая внутренняя функция считает `ёмкость × процент / 100` и двигает пул **на разницу с прошлым отчётом этого же устройства**. O(1), перебора устройств нет, газ не растёт с размером сети;
- защита от отрицательного остатка при миграции (клампинг вместо revert — падение в пути чеканки недопустимо);
- 🔴 **`recordEnergyConsumption` больше НЕ трогает пул.** Разряженная батарея сама сообщит меньший заряд следующим пакетом; вычитание здесь дало бы **двойной учёт** тех же кВт·ч. Функция оставлена живой (Settlement и его интерфейс менять не пришлось), расход виден в событии.

**`OracleRouter.sol`**
- `chargeLevelPercent` пробрасывается в MintingEngine (раньше терялся).

**Чеканка не изменена.** Заряжаешь — получаешь ноты, те же лимиты, те же подписи.
**Дашборд и SDK не изменены** — читают то же число через ту же view-функцию.

## Тесты

**Новый файл `test/PoolAccounting.t.ts` — 7 тестов, все зелёные.** По одному на каждую утечку плюс проверка, что чеканка не пострадала и что заряд >100% отвергается. Файл намеренно самодостаточный — не использует `test/helpers/fixtures.ts`, чьи значения устарели до перевода кВт·ч в 18-значную шкалу.

**Задето и починено 11 существующих тестов:** семи добавлен недостающий аргумент, три переписаны под новое поведение (они утверждали отменённый дизайн: «пул уменьшается при `recordEnergyConsumption`», «падает при списании больше остатка», старая формула индекса).

### Порядок миграции (важно — повторять при любом апгрейде работающей сети)

У устройств, зарегистрированных **до** апгрейда, поле `lastReportedEnergy` читается как 0, а старый накопленный итог остаётся. Первый же новый пакет складывается со старым итогом → **двойной счёт**.

Выполнено:
1. Апгрейд обоих контрактов (`scripts/upgrade.ts`). Пул не изменился, демо осталось живым.
2. `scripts/seed-test-data.ts` — 3 VPP (Техас / Берлин / Сидней) × 5 устройств. Ключи → `deployments/seed-arbitrumSepolia.json`.
3. **`scripts/push-fleet-measurements.ts` (новый)** — по одному подписанному замеру с каждого устройства. 15 из 15 успешно. Пул стал `139.0` при реальных `121.5` — расхождение **ровно 17.5**, то есть старый остаток, что подтвердило диагноз до цифры.
4. **`scripts/resync-pool.ts` (новый)** — `TARGET_KWH=121.5`. Разово выставляет пул в истинную сумму отчётов устройств через `adminSetTotalVerifiedEnergy`.

**Нулей на дашборде не было ни секунды** — порядок выбран так, что пул сразу шёл с завышенного на правильное, минуя ноль.

## На мейннет это не переносится

Мейннет стартует с пустого контракта: нет старого итога, нет устройств без `lastReportedEnergy`. Описанная миграция — **след обновления уже работавшей сети**, а не свойство кода.

## Что осталось открытым (не про эту правку)

- **Правило свежести.** Устройство, замолчавшее навсегда, продолжает держать свою долю в пуле. Нужна публичная функция: молчит дольше N эпох → доля выпадает; вызвать может кто угодно, контракт сам смотрит на часы. В `DeviceRecord` уже есть флаг `active` — возможно, использовать его.
- **27 красных тестов** (шкалы + версия ProtocolGovernance). Публичный репозиторий стоит ссылкой в деке; статус набора стоит один раз описать в README, чтобы «у них тесты сломаны» читалось как «они знают, что устарело и почему».
- **`totalEnergyEverVerified`** упоминается в `dashboard/README.md`, но в контрактах такой функции нет.
- **Аудит** (OpenZeppelin / Trail of Bits) и **Chainlink + проверка DSO** — Phase 1, к учёту отношения не имеют.

## История вопроса

Турпал нашёл 29.07, затем **снизил оценку под давлением Мага, не имея нового факта** — нарушение доктрины («переубеждать должен факт или расчёт, не напор»). Маг вопросов не принял и потребовал разобрать по коду. Разбор показал, что данные для правильного числа уже передаются и уже подписаны — их просто не читали. Находка целиком результат того, что Маг не согласился с общими формулировками.
